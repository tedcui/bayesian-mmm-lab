## Source data contract and separation of concerns

The three authoritative *source-aligned* tables are:

`SYNTHETIC_SOURCE` and `SOURCE_*` are generic aliases used in this portfolio;
they are not physical source-system table names.

| Table | Grain | Candidate identity |
|---|---|---|
| `SYNTHETIC_SOURCE.SOURCE_TRANSACTIONS` | Submitted transaction detail, **not a basket** | `TRANSACTION_ID` (validate; do not assume unique) |
| `SYNTHETIC_SOURCE.SOURCE_STORES` | Submitted store reference/crosswalk | `(SUBMITTER_ID, STORE_ID)` as observed lookup |
| `SYNTHETIC_SOURCE.SOURCE_BRANDS` | Submitted product/item reference, **not just commercial brand** | `(BRAND_ID, UPC14)` as observed lookup |

Simulated IDs use deterministic uppercase **32-character hexadecimal strings** for the source's documented 32-character converted identifiers; preserve `SUBMITTER_ID` length 36 and UPC-14 leading zeros. Use strings for exact 19-digit identifiers if necessary to avoid JavaScript precision loss. Preserve timezone-aware versus timezone-naive timestamp distinctions. Preserve nullable flags and quality/status columns without inventing original source business meanings. In the synthetic data, document any chosen flag codes and `PRICE` semantics as **simulation-only conventions**.

Observed sample SQL join contracts:

```sql
-- transaction -> store
ON t.SUBMITTER_ID = s.SUBMITTER_ID
AND t.STORE_ID = s.STORE_ID

-- transaction -> submitted product reference
ON t.BRAND_ID = b.BRAND_ID
AND t.UPC14 = b.UPC14
```

`UPC14` may be null. Normal equality joins must not treat null as matching null without an explicit documented rule. Do not silently add `SUBMITTER_ID` to the product join: document and test whether that is appropriate for the synthetic reference's generated ID scope. Keep `STORE_ID` distinct from `MASTER_STORE_ID` and `BRAND_ID` distinct from `MASTER_BRAND_ID`. Do **not** directly join stores to brands outside transaction activity.

The three supplied tables do **not** contain independently defined planned coupon, retailer, or digital advertising spend; they also do **not** contain a competitor index or a true store-availability measurement. For the full 3-channel MMM, create explicitly **additional synthetic auxiliary source tables**:

- `SIM_MARKETING_PLAN`: segment × week × channel planned spending/exposure, created before simulated sales, with 3 channels and scenario-relevant bounds.
- `SIM_MARKET_CONTEXT`: segment × week exogenous competitor conditions, planned price index, market/availability index, and any needed scenario controls.

These are **project additions**, not user-supplied silver tables. Document them separately and preserve a strict three-source-only ETL demonstration path. A strict three-table dataset can describe coupon/redemption metrics but cannot honestly support the planned-spend digital MMM or budget optimizer without additional information.

**Generator causal ordering:** define segment/context and planned marketing -> calculate synthetic latent expected demand using adstock, saturation and controls -> draw realized sales quantities -> split those quantities into realistic store/product/basket/line records -> assign redeemed discount/flag data -> ingest/validate/join/aggregate -> construct `model_ready`. Never generate `model_ready` independently.

## Data and ETL acceptance criteria (M2A/M2B)

- Default 6 geography-defined segments, 120 consecutive weekly periods, and 3 promotional channels. The six segments are **business-defined groups of stores**, derived from documented store geography, **not unsupervised K-means clusters**.
- Generate manageable local-scale data (parameterized target ~100k–250k transaction lines, 120–300 stores, 24–60 submitted item records), clearly not attempting to reproduce multi-billion-row production scale. The generator may adjust exact counts to preserve model-relevant outcomes.
- Generate all 44 transaction, 42 store, and 19 product source columns, honoring documented types/nullability where possible. Separate raw/source-aligned columns from synthetic source metadata and derived ETL fields.
- `FILE_SUBMISSION_ID`, `SUBMITTER_ID`, source timestamps and original/current product fields remain traceable.
- Simulate basket IDs with multiple line records; optionally loyalty IDs; realistic quantities, pricing, promotional flags and mutually documented discount semantics.
- Simulate optional controlled anomalies and late submissions; join failures/ambiguities must be reported, not silently filtered. Prefer a clean default with a separate deterministic bad-data fixture so the main MMM model remains interpretable.
- Distinguish event date from submission and processing date. Validate `TRANSACTION_ID` uniqueness rather than presuming it; if needed use an ETL-only physical-row ID to preserve detail records.
- A validated, nonmultiplying enrichment joins stores/products. Unmatched rows survive with quality flags; only explicitly justified rows are excluded from the analytic mart, with reconciliation counts.
- Produce **exactly 720 segment-week rows** for the default 6×120 complete panel, including documented zero-sales weeks when truly observed. Do not replace absent/incomplete submissions with zero sales silently.
- Save `data/metadata/ground_truth.json` separately; training data must not include true latent components, coefficients or response parameters.
- Aggregated `sales_units` must equal the sum of eligible detail `QUANTITY` for each segment/week and overall, with explicit differences for exclusions/unmatched entries.
- `marketing_spend_*` predictors derive from `SIM_MARKETING_PLAN`, **not** realized discounts or redeemed-promotion flags.
- Use weeks 1–100 for training and weeks 101–120 for holdout, preserving pre-holdout adstock state. Fit scalers and other learned transforms on training data only.
- All generated data, marts and model outputs include deterministic seeds, hashes and lineage. Rerunning M2A/M2B with identical inputs produces identical content, modulo documented metadata timestamps.

See `docs/SOURCE_SCHEMA_AND_ETL.md` and `docs/MODELING_DATA_CONTRACT.md` for column-level details, formulas and tests.

## Bayesian models (M3)

Fit three genuine specifications using the **ETL-produced** `data/processed/model_ready` panel:

1. Complete pooling: common channel response across segments.
2. No pooling: independent channel effects for each segment.
3. Hierarchical partial pooling: segment-level channel effects from population distributions, with uncertainty.

Use appropriate controls, trend, seasonality, adstock and saturation; share adstock/saturation across segments initially. The model must be compatible with the ground-truth-generating mechanism. Verify current pinned PyMC-Marketing API; use transparent lower-level PyMC if necessary and document why.

Notebook 01 explores **the downstream mart and source-to-mart lineage**; notebook 02 specifies, fits and saves three Bayesian models; notebook 03 evaluates convergence (R-hat/ESS/divergences), posterior predictive checks, time holdout, interval coverage, prior sensitivity, contribution recovery, and pooling comparisons. Examine sparse-information segments without asserting partial pooling always wins.

**Causality caveat:** in real observational markets, targeted promotion and pricing can be endogenous. Synthetic ground-truth recovery shows the code works under specified generating assumptions, not that observational promotional effects are automatically causal. A counterfactual or budget recommendation inherits the model's causal assumptions. Expose this caveat in notebook, exports and UI.

Python is reference implementation; TypeScript calculations must pass deterministic parity fixtures. Same scenario as baseline must produce zero incremental expected sales. Optimize only after manual simulation works; no ROI language without clearly defined margin/value and spend-cost semantics.
