# M4 fitted-model browser export contract

The five files in `web/public/model-data/` are generated by `uv run mmm-export` from the validated M2B panel, all three actual M3 posterior NetCDF files, and the M3 evaluation report. No fitting occurs during export or a frontend build. The browser receives no transaction details, contacts, source identifiers, or NetCDF files.

## Lineage and version checks

`manifest.json` uses schema version `m4-1`. Its stable `bundle_id` is SHA-256 of the schema version, model-input hash, fit-manifest hash, and evaluation hash. It records the source manifest and schema hashes, ETL manifest and version, model input, fit/evaluation artifacts, and each posterior's hash. The exporter checks all input hashes and rejects a posterior with stale coordinates, missing pooling specification, divergences, or maximum R-hat over 1.01. Poor coefficient recovery is **retained and disclosed**, not converted into a pass/fail sampling gate.

Each of the other four files carries the same schema version and `bundle_id`. Manifest entries record their byte length and SHA-256. `web/src/lib/data.ts` checks file bytes and hashes when loading, then validates schema, dates, segment/channel keys, units, finite numbers, and numerical reconciliation. The TypeScript types are in `web/src/types/modelData.ts`. The manifest timestamp can change on regeneration; the payload hashes remain stable for the same input artifacts and export seed.

## Payloads

| File | Grain and content |
|---|---|
| `manifest.json` | Versions, provenance, dates, labels, units, payload hashes, limitations. |
| `overview.json` | 720 segment-week observed sales, planned spend, partial-pooling expected-sales credible summaries, separate future-observation predictive summaries, residuals; 21 period/segment aggregates. |
| `contributions.json` | 720 segment-week posterior baseline and three modeled channel contribution summaries; 21 aggregates and reconciliation to expected sales. |
| `segments.json` | 54 pooling × segment × channel maximum-effect estimates, 90% parameter intervals, synthetic evaluation-only truth, diagnostics, conditional holdout metrics, and segment training profiles. |
| `simulator.json` | 96 reproducibly selected **joint** partial-pooling posterior draws, each with chain/draw index and all coefficients/shapes; 108 weeks of prior spend, 12 weeks of baseline planned spend and fixed controls for each segment, exact model transformation/scales, and spend bounds. |

The partial-pooling fit is the **pedagogical reference** for weekly decomposition and the eventual manual simulator. It is not selected as the statistically best model. In this synthetic run, no pooling has better coefficient recovery (17/18 true effects inside its 90% intervals versus 15/18 for partial pooling), although holdout sales accuracy is essentially tied. The comparison export includes all three specifications and makes this visible.

The simulator baseline is a **retrospective replay of holdout weeks 109–120**, not a prospective forecast. Planned spend and pre-outcome market context are held fixed. The allowed spend range for each segment/channel is zero through the highest observed plan in weeks 1–120; `training_max_usd` and `training_p95_usd` allow the future UI to flag proposals outside training support. This range is a support guard, not evidence that all changes within it are causally identified. M6 will implement and test scenario calculations against the saved joint draws.

## Numerical interpretation

The fitted mean is baseline plus three channel contributions **within each posterior draw**. For an aggregate, the exporter first sums all selected segment-weeks and components within each draw, then computes mean and 5th/50th/95th percentiles. Adding published component interval endpoints is mathematically invalid and fails a numerical test. `residual_to_expected_mean_units = observed_sales_units - posterior_mean_expected_sales_units`, subject to four-decimal output rounding.

`expected_sales_units` intervals describe uncertainty in the conditional expected mean. `predictive_sales_units` intervals additionally include the fitted Normal observation noise; predictive draws use a fixed export seed. These are conditional on planned spend and pre-outcome context, not unconditional future demand forecasts. Sales are units, planned spend is USD, and time is Monday-start week. `segments.json` coefficient intervals describe parameters, not future observations or marginal sales per dollar.

The generator's known truth is read from the M3 evaluation artifact only for `segments.json`; it is never a fitting feature. The partial model misses some true segment/channel effects. Correlated campaigns, targeting, prior sensitivity, and the synthetic nature of the data limit interpretation. Modeled contributions and scenario differences are assumption-dependent estimates, **not experiment-validated causal lift or profit**.

## Reproduce and verify

From `modeling/`:

```sh
uv run --locked mmm-export
uv run --locked pytest -q
```

From `web/`:

```sh
npm run typecheck
npm test
npm run build
```

The Python tests check hashes, reproducibility, dates, draw-level aggregation, reconstruction, joint draw indexing, and public payload limits. Four regeneration checks require the local, gitignored posterior NetCDF files and skip in ordinary CI when those files are absent; CI still checks committed export hashes and lineage without fitting MCMC. The TypeScript tests validate the actual five files and reject mixed versions, invalid units/numbers, broken reconciliation, and duplicate draw IDs. M5 analytical pages consume these validated exports; the scenario engine remains a later milestone.
